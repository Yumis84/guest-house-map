# Бронирование отдельных номеров и домиков: контракт v1

Статус: проект; НЕ подключён к production n8n и Google Sheets.

## Выявленное ограничение
Существующий n8n `WEB_BOOKING_GUEST_HOUSES` принимает `house_id`. В подпроцессе `Оформление брони Краснолесье` конфликт дат проверяется только по `house_id`, а успешная запись в Google Sheets получает статус `Подтверждено`. Следовательно, нельзя отправлять туда запросы по `unit_id` без изменения backend.

## Новый запрос
```json
{
  "schema_version": 2,
  "property_id": "house_004",
  "room_type_id": "point_aframe",
  "unit_id": null,
  "check_in": "2026-11-10",
  "check_out": "2026-11-12",
  "guests": 2,
  "guest_name": "...",
  "phone": "...",
  "request_id": "client-generated-uuid"
}
```

Гость выбирает категорию; конкретная unit назначается сервером после проверки занятости. `unit_id` допускается только при явном выборе конкретного домика. `house_id` остаётся legacy alias, но не используется как ключ конфликта для категорий с несколькими unit.

## Алгоритм backend
1. Проверить существование property, room_type и их связь, количество гостей и корректность дат.
2. Найти все активные units категории.
3. В одной сериализованной операции проверить пересечения `existing.check_in < requested.check_out && existing.check_out > requested.check_in`.
4. Выбрать доступную unit и создать запись с `property_id`, `room_type_id`, `unit_id` и `request_id`.
5. Повторный `request_id` не должен создавать новую бронь.
6. При отсутствии свободных units вернуть `unavailable`, без записи.
7. Для заявок до подтверждения владельцем сохранять `pending`; статус `confirmed` только после подтверждения. Отменённые заявки не блокируют даты.
8. Нельзя одновременно обрабатывать два конкурирующих запроса на один инвентарь без блокировки/очереди. Google Sheets сам по себе транзакций не даёт.
9. Не записывать контакты гостей в GitHub и публичные JSON.

## Google Sheets
Вкладка «Бронирования»: сохранить существующие колонки; после проверки добавить `property_id`, `room_type_id`, `unit_id`, `request_id`, `schema_version`. Старые брони должны сохраняться. До миграции старых броней по `house_004` требуется ручное сопоставление с конкретными A-frame; иначе нельзя утверждать, что домики свободны.

## Acceptance до включения
- Две брони одной unit с пересекающимися датами: вторая отклонена.
- Два разных A-frame на одни даты: обе возможны.
- Три A-frame заняты: четвёртый запрос отклонён.
- Выезд 12-го и заезд 12-го: не пересекаются.
- Повтор одного request_id: одна запись.
- Невалидный room_type_id, чужой property_id, гости сверх capacity: отказ.
- Конкурентные запросы: не больше одного подтверждения на unit.
- Старые брони, не сопоставленные с unit: не игнорируются.
- Отказ сервера/Sheets: не показывать «подтверждено».
- Остальные объекты и действующий webhook сохраняют прежнее поведение.

## Выпуск
Подготовить тестовую копию n8n workflow, тестовые данные без реальных гостей и отдельный webhook. После прохождения acceptance согласовать переключение сайта и backend; до этого UI категорий остаётся информационным, кнопка отправки заявки на конкретную категорию отключена.
